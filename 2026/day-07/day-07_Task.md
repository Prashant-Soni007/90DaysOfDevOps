# Day 07 – Linux File System Hierarchy & Scenario-Based Practice

## Part 1: Linux File System Hierarchy

### Core Directories

**`/` (root)**
The top of the entire filesystem tree — every other directory is a subdirectory of `/`.
```
lrwxrwxrwx   1 root root     7 bin -> usr/bin
drwxr-xr-x  72 root root  4096 etc
drwxr-xr-x   4 root root  4096 home
```
I would use this when navigating between top-level directories or writing scripts that need absolute paths.

**`/home`**
Contains a personal directory for each non-root user on the system.
```
drwxr-xr-x 7 root   root   4096 claude
drwxr-x--- 2 ubuntu ubuntu 4096 ubuntu
```
I would use this when looking for a specific user's files, SSH keys, or personal configs.

**`/root`**
The root user's home directory (separate from `/home` since root needs its own space even if `/home` isn't mounted).
```
-rw-r--r--  1 root root 3106 .bashrc
drwxr-xr-x  4 root root 4096 .config
drwx------  2 root root 4096 .ssh
```
I would use this when troubleshooting as the root/admin user or checking root's shell config and SSH setup.

**`/etc`**
Holds system-wide configuration files for installed software and services.
```
drwxr-xr-x 2 root root 4096 ImageMagick-6
drwxr-xr-x 2 root root 4096 PackageKit
drwxr-xr-x 8 root root 4096 X11
```
I would use this when changing a service's configuration (e.g., editing an app's config file before restarting it).

**`/var/log`**
Stores log files generated by the system and services — the first place to check during an incident.
```
lrwxrwxrwx 1 root root   39 README -> ../../usr/share/doc/systemd/README.logs
-rw-r--r-- 1 root root 20360 alternatives.log
-rw-r--r-- 1 root root 61229 bootstrap.log
```
I would use this when a service crashes or behaves unexpectedly and I need to see what actually happened.

**`/tmp`**
Temporary storage for short-lived files, usually cleared on reboot.
```
drwxr-xr-x 2 root root 4096 day06
drwxr-xr-x 2 root root 4096 hsperfdata_root
drwxrwxrwx 3 root root 4096 phantomjs
```
I would use this when testing something quickly without worrying about cleaning it up permanently.

### Additional Directories

**`/bin`**
Essential command binaries needed even in single-user/recovery mode (on this system, symlinked to `/usr/bin`).
```
lrwxrwxrwx 1 root root 7 /bin -> usr/bin
```
I would use this when a basic command like `ls` or `cp` isn't found and I need to check if core binaries exist.

**`/usr/bin`**
Non-essential (but still common) user command binaries — the majority of installed CLI tools live here.
```
-rwxr-xr-x 1 root root 2064864 Xvfb
-rwxr-xr-x 1 root root   55744 [
-rwxr-xr-x 1 root root    4934 activate-global-python-argcomplete
```
I would use this when checking which version of a tool is installed or confirming a package installed correctly.

**`/opt`**
Holds optional, third-party, or manually installed applications that don't follow the standard package layout.
```
drwxr-xr-x 3 root root 4096 google
drwxr-xr-x 6 root root 4096 pw-browsers
drwx------ 2 root root   39 rclone
```
I would use this when installing or troubleshooting a third-party app that was dropped in manually rather than via a package manager.

## Part 2: Scenario-Based Practice

### Scenario 1: Service Not Starting

```
Step 1: systemctl status myapp
Why: Shows immediately if the service is active, failed, or stopped, and often
     prints the last error line right in the status output.

Step 2: journalctl -u myapp -n 50
Why: Pulls the last 50 log lines for the service — the actual error (missing
     config, port conflict, permission issue) usually shows up here.

Step 3: systemctl is-enabled myapp
Why: Confirms whether the service is set to start on boot at all — if it's
     disabled, that alone explains why it didn't come up after the reboot.

Step 4: systemctl start myapp
Why: After identifying and fixing the root cause from the logs, attempt to
     start it manually and watch for it to hold "active (running)".
```

### Scenario 2: High CPU Usage

```
Step 1: top
Why: Live view sorted by resource usage by default — quickly spot which
     process is consuming the most CPU.

Step 2: ps aux --sort=-%cpu | head -10
Why: A non-interactive snapshot sorted by CPU%, useful for logging the
     top offenders or sharing output with a teammate.

Step 3: Note the PID and command name of the top process
Why: Needed for every next step — restarting, killing, or inspecting the
     process requires its exact PID.

Step 4: ps -o pid,pcpu,pmem,comm -p <PID>
Why: Confirms the specific process's CPU and memory usage in isolation,
     without noise from every other process on the system.
```

### Scenario 3: Finding Service Logs

```
Step 1: systemctl status docker
Why: Confirms the service exists and is managed by systemd before assuming
     journald has logs for it.

Step 2: journalctl -u docker -n 50
Why: journald is the standard log store for systemd-managed services —
     this pulls the last 50 lines directly.

Step 3: journalctl -u docker -f
Why: Follows logs in real time (like tail -f), useful when reproducing an
     issue live and watching for the exact moment it fails.
```

### Scenario 4: File Permissions Issue

```
Step 1: ls -l /home/user/backup.sh
Look for: -rw-r--r-- (no 'x' = not executable, which explains the
          "Permission denied" error).

Step 2: chmod +x /home/user/backup.sh
Why: Adds execute permission for owner, group, and others so the script
     can actually run.

Step 3: ls -l /home/user/backup.sh
Look for: -rwxr-xr-x (the 'x' now confirms it's executable).

Step 4: ./backup.sh
Why: Re-run the script to confirm the fix actually resolved the issue.
```

## Why This Matters
Knowing where configs, logs, and binaries live — and having a repeatable troubleshooting flow (check status → check logs → check permissions/boot config) — turns guesswork into a fast, confident response during real incidents or interviews.
